# flash-agent: review, 2026-09-15

Scope: the whole repo at `29ff918`: `flash-mcp` (MCP server, SDK client, service), `dsh-flash-guard`,
`dsh-subagent-flash`, the `flash-service` profile, the `flash-orchestrator` preset, `install.mjs`, and
the tests. This document is meant to be handed to someone else to act on. Every finding has a location,
a reason, and a concrete change. Priorities: **P0** fix before anyone else uses this, **P1** fix before calling it
stable, **P2** worth doing.

How the review was done: I read every file. `npm test` passes (83/83). I also ran a probe script
directly against `decideToolCall` to check whether the guard can be bypassed (results in §1.1). I did not
run the live suite (`npm run verify`), because it runs writing workers against the real repository
(see §1.3). I looked at the installed Harness packages only far enough to check which protocol surface
they expose.

---

## 0. Executive summary

The pieces are well built and carefully documented. The contract in `dsh-subagent-flash` is small and
correct, and the MCP and SDK clients are clean. The problems come from three design decisions, not
from sloppy code:

1. **An LLM relays every call.** Each `flash_task` or `flash_batch` starts a Flash "dispatcher" agent. It
   has to copy the task (or a script plus all of its arguments) into a tool call "verbatim", and then it
   reads the whole result back in. That costs latency and tokens, the copy is never checked, and the
   dispatcher is an agent with a full, writable tool surface that reads text supplied by the caller.
   This is the biggest architectural issue, and most of the complexity in `service.js` exists to work
   around it (§2.1).
2. **Safety depends on a shell denylist.** `flash-guard` is presented as the part that carries the load,
   but it can be bypassed with ordinary shell. Examples: `rm -rf "$(pwd)"`, `bash -c "rm -rf ."`,
   `git -C . clean -fdx`, `grep -r API_KEY .`, `source .env`. The incident in `29ff918` is a symptom
   of this whole class of problem, and patching individual shapes will not close it. Deletion has to be
   recoverable by construction, and secrets have to be protected by the OS (§1.1, §2.2).
3. **Several promises are only text.** `cwd` is not a fence: it is a line in the prompt, and every write
   is confined to the whole root. `results[i].status: "ok"` means "the worker returned text", not "the
   worker succeeded". Fleet results are scraped from rendered tool output, which the README says the
   project avoids (§1.4, §2.3).

On integration: the tools block for up to 15 minutes, don't send progress, and ignore client timeouts.
Codex's default MCP tool timeout is about 60 s, so most calls would fail there. Permissions can't tell
read-only calls from writing ones, because `mode` is an argument rather than a tool name (§4).

## 1. P0: safety and correctness

### 1.1 `flash-guard` bypasses (confirmed)

`packages/dsh-flash-guard/lib/index.js`. Probe: `decideToolCall({name, args, cwd: ROOT, home: HOME, settings})`
with default settings. Everything below came back **ALLOW**:

| Class | Command / call | Why it passes |
|---|---|---|
| Delete root | `rm -rf "$(pwd)"`, `rm -rf $PWD` | tokens are not expanded; `$(pwd)` resolves to `<root>/$(pwd)` |
| Delete root | `cd .. && rm -rf project` | each simple command is resolved against the agent cwd, and `cd` is ignored |
| Delete root | `bash -c "rm -rf ."`, `sh -c '…'` | the quoted program is one token; `-c` payloads are never re-parsed |
| Delete root | `mv . /tmp/gone`, `rsync -a --delete empty/ ./` | only `rm`/`rmdir`/`shred`/`find`/`xargs` count as deletion |
| Delete root | `node -e "fs.rmSync('.',{recursive:true})"`, `perl -e 'rmtree'` | inline code is scanned for secrets only |
| Delete tree | `find . -name "*" -delete`, `find . -path "*" -exec rm -rf {} +` | any `-name` counts as narrowing (`FIND_NARROWING`, l.299), even `*` |
| Git | `git -C . clean -fdx`, `git -c k=v reset --hard` | `destructiveGitReason` (l.336) drops `-x` flags but keeps their values, so `.` or `k=v` becomes the "subcommand" |
| Git | `git push origin +main`, `git branch -D main`, `git stash drop`, `git update-ref -d HEAD` | not in the set |
| State write | `echo x \| tee .git/config`, `sed -i … .git/config`, `cp evil .git/hooks/pre-commit` | only redirects and file tools are write-checked; `cp`/`tee`/`sed -i` targets are not |
| State write | `apply_patch {patch: "*** Update File: .git/config"}` | the patch body is not a `PATH_ARGUMENT` |
| Secret read | `grep -r API_KEY .`, `rg SECRET`, fs tool `grep {path: "."}` | a recursive search reads `.env` without naming it |
| Secret read | `source .env`, `while read l; do …; done < .env`, `cat .en""v`, `cat .env*` | `source`/`<`/quote-splicing/globs are not recognised |
| Secret read | `read ~/.npmrc`, `cat ~/.kube/config`, `cat ~/.zsh_history` | not in the lists (and `.npmrc` is only write-protected) |

Also:
- **The `bash` tool takes a `workdir` argument** (`dsh-tool-bash`), but `cwdOf` (l.568) only reads
  `agent.meta.cwd`. Relative targets are therefore resolved against the wrong directory whenever
  `workdir` is set.
- **Missing high-value secrets.** `homeProtectedPaths` covers `~/.dsh` but not `~/.codex` (holds `auth.json`),
  `~/.claude`, `~/.config/claude`, `~/.kube`, `~/.pypirc`, `~/.cargo/credentials*`,
  `~/.terraform.d`, `~/.azure`, `~/.config/op`, `~/Library/Keychains`, browser profiles, or shell history.
  `.npmrc` and `.mcp.json` hold tokens but are only write-protected. The external agents this MCP server
  is built for store their own credentials in exactly those places.

**Change (short term):** keep the guard, but treat it as a tripwire and fix it on those terms:
- Deny whenever a deletion or state-write target contains an unexpanded `$`, a backtick, or `$(`. Refusing when
  unsure is already the stated policy.
- Parse `sh|bash|zsh -c <payload>` again, recursively, and apply the same inline-code scan to deletion
  primitives (`rmSync`, `rmtree`, `shutil.rmtree`, `unlink`, `FileUtils.rm_rf`).
- Treat `cd` inside a compound command as making the command unresolvable: deny deletions that follow it.
- Honour `args.workdir` / `args.cwd` in `cwdOf`.
- Parse git global options (`-C <path>`, `-c <kv>`, `--git-dir`, `--work-tree`) before reading the subcommand.
  Add `push +ref`, `branch -D`, `stash drop|clear`, `update-ref -d`, `reflog expire`, `gc --prune=now`.
- Write-check destination arguments of `cp|mv|install|tee|sed -i|ln|rsync|dd of=`.
- `FIND_NARROWING` must require a pattern that isn't a bare `*`.
- Treat `source`/`.` and `<` input redirects as reads.
- Add the credential paths listed above, and make `.npmrc`/`.mcp.json` secrets.
- Put every row of the table above into `test/index.test.mjs` as regression tests.

**Change (the real fix):** see §2.2. The guard cannot be made complete, so both deletion and exfiltration
need a boundary that doesn't depend on parsing.

### 1.2 The dispatcher is an unrestricted agent fed by caller text

`service.js:774`, `:799`; `profiles/flash-service/cordis.patch.yml`. The dispatcher session is an ordinary SDK
agent in a `workspace-write` profile that composes `dsh-base`, so it has bash and fs tools. The caller's task
text is pasted straight into its prompt between `<<<TASK … TASK` markers. A task that contains `TASK` on its own
line, or simply says "don't delegate, run X", lets the caller's text drive the dispatcher. The
`NOT_DELEGATED` error path exists because this already happens. The guard applies to the dispatcher too, so
§1.1 applies here as well. The only thing the `toolFilter: deny: [flash]` on `tool-flash` restricts is the *child*.

**Change:** remove the dispatcher (§2.1). If that has to wait, give the dispatcher an allowlist of only
`flash`/`workflow` (e.g. a dispatcher persona row with `tools.restrict({allow: [...]})`, if the SDK agent can be
scoped). Put caller text in a delimiter it can't contain (a random nonce per call), and fail the call if the child's
first request doesn't contain that nonce plus a hash of the task (§2.1, option C).

### 1.3 The live suite still runs writing workers against the real repository

`packages/flash-mcp/test/verify-live.mjs:38` defaults `--root` to `/Users/thomas/Projects/flash-agent`. Only the
`guard` stage uses a decoy. The `task`, `local`, `batch`, `readonly`, `hostile`, `reuse`, and `escape` stages all run
`workspace-write` Flash workers with bash on the caller's checkout, and with the bypasses in §1.1 any of them can
do what the guard stage once did. `SDK_DIR` (l.31) is also hardcoded to a Homebrew path.

**Change:** by default, every stage runs in a fresh temporary `git clone --local` (or `git worktree add`) of the repo.
`--root` becomes an explicit, opt-in override, with a loud warning. Resolve the SDK via `import.meta.resolve` /
`createRequire` from the `dsh` install found on PATH, with `MCP_SDK_DIR` as an override. Remove every
`/Users/thomas` literal from code and the README.

### 1.4 `cwd` is presented as a fence but isn't one

`service.js:382` checks that `cwd` is under the root, then only *writes it into the prompt*
(`buildChildPrompt`, l.914). The sandbox root is the SDK `initialize.cwd`, which is fixed per process to the
service root. The guard falls back to `process.cwd()`, which is the same root. A `flash_batch` with `cwd: "packages/a"`
can therefore write anywhere under the root. The README ("the fence for the per-call `cwd`") and the tool
schema description imply otherwise.

Minor bugs in the same function:
- `relation.startsWith('..')` rejects legitimate directories named `..foo`. Use
  `relation === '..' || relation.startsWith('..' + sep)`.
- A path that doesn't exist yet is not realpath'd, so it's never checked whether its closest existing parent
  is a symlink out of the root.

**Change:** either make `cwd` real, or stop calling it a fence. Ways to make it real: per-session cwd if the SDK
protocol gains it; the worktree model in §2.2, where the sandbox root *is* the per-call directory; or a guard
setting fed per session. Until then, reword the schema and README to "the worker is *told* to work here;
confinement is the service root".

### 1.5 Fleet status is inferred from "returned text"

`service.js:62`: `ok: text !== null && text !== undefined`. A worker that ends with
`status: error` / `stopReason: max_turns` but still produced a final message is reported as
`results[i].status: "ok"`. The contradiction only shows up in the separate `workers[]` array and in a
generic warning (l.489).

**Change:** per-task `status` should come from the engine's member `outcome`, or from `subagent.finished.status`
(both are already collected). The script's return value should be used only for the text.

## 2. Architecture

### 2.1 Remove the LLM dispatcher hop

**Today:** MCP call → SDK `session/prompt` with a dispatcher prompt → a Flash model reads it → emits a `flash`
(or `workflow`) tool call whose arguments are a *model-generated copy* of the task (or of `BATCH_SCRIPT` plus a
JSON `args` holding every item prompt) → the tool runs → the result is fed back to the dispatcher → it emits
`DELEGATED` → the service scrapes the result out of events.

Costs:
- **Latency and tokens.** At least two extra model turns per call. Output tokens scale with the total task size,
  and output is the slowest part of generation. For a 16-task fleet the dispatcher re-types the script and every
  item prompt (with `WORKER_RULES` and `cwd` repeated 16×, JSON-escaped). The workflow result (up to 250 000
  chars, `tool-workflow.maxResultChars`) then goes back into the dispatcher's context only so it can say
  `DELEGATED`.
- **Integrity.** Nothing checks that the relayed task equals the one sent. A Flash model "copying verbatim"
  several KB of JSON will sometimes paraphrase, truncate, or break the escaping. Setting `FLASH_MAX_TOKENS`
  (which applies to *all* SDK agents, dispatcher included) silently caps how much it can relay.
- **Safety.** §1.2.
- **Complexity.** `NOT_DELEGATED`, `describeParent`, the 40-event trace, the multi-child warning,
  `looksLikeWorkflowResult` / `extractWorkflowValue` / `parseWorkflowHeader`, and the three-way pairing fallback
  in `#buildBatchResult` exist only because an LLM sits in the middle.

**Options, best first:**

- **A. Deterministic entry point in the protocol.** The installed `dsh-sdk-protocol` exposes only
  `initialize`, `session/prompt`, `shutdown` plus four notifications. There is no way to start a subagent or a
  workflow run directly. Ask upstream for `subagent/start {provider, prompt, toolFilter?}` and
  `workflow/run {script, args, meta}`, returning structured results. This is the right long-term seam.
- **B. A command row in the service profile (doable now, needs verification).** Harness already has a
  deterministic command seam: `ctx.commands.register` (used by `dsh-command-compact`). Add a
  `dsh-flash-dispatch` row that registers e.g. `/flash-run <base64-json>`. Its handler calls
  `ctx.subagents.getProvider('flash').start(...)` for a task, or the `workflowEngine` for a fleet, and puts the
  structured result into a session event. **First check whether `session/prompt` routes slash commands in the
  SDK app the way the interactive app does.** If it does, no model runs outside the workers, and the `flash`
  tool, the dispatcher prompt, and the text scraping all go away.
- **C. Keep the dispatcher, but verify it.** Give it an allowlist of only `flash`/`workflow`. Put a per-call nonce
  and a SHA-256 of the child prompt in the child prompt, and compare them against the child's logged
  `request/header` / first user message. On mismatch, fail with `RELAY_MISMATCH`. For batches, pass *only item ids*
  through the model and have the script fetch the item bodies (e.g. from a file the service writes under a
  service-owned temp dir that the workers can read) so the relayed payload stays tiny. Set the workflow tool's
  `maxResultChars` low, since the service reads per-member results from events rather than from the rendered
  text (see 2.3).

Recommendation: do **B** now (a spike of about half a day decides whether it works), push for **A** upstream, and
use **C** only as a fallback.

### 2.2 Make the dangerous outcomes recoverable, not merely detected

The guard is a denylist over an open language (§1.1). Two structural changes remove the need for it to be
complete:

1. **One worktree per call (or per fleet member).** The service does
   `git worktree add --detach <svc-tmp>/<callId> HEAD` (or a copy-on-write clone, `cp -c` on APFS, for
   non-git roots) and runs the worker there, with the sandbox root = that worktree. On completion it returns
   a structured diff: `filesChanged`, `diffstat`, and optionally a patch or a branch name. Then it either
   applies the diff to the caller's root or leaves the choice to the caller: add `apply: "auto" | "none"`,
   defaulting to `none`, plus a `flash_apply {callId}` tool. Consequences:
   - `rm -rf` of anything the worker can reach deletes a throwaway checkout;
   - parallel fleet members stop overwriting each other's edits to the same file (today they share one tree);
   - the expensive caller gets a machine-generated "what changed" instead of trusting "name every file
     you changed";
   - `cwd` becomes a real fence (§1.4);
   - read-only mode could become "never apply" instead of a second process (though keep the sandbox-level
     read-only; see 2.5).
   Because the sandbox root is fixed per process (`initialize.cwd`), this needs either a per-session
   workspace in the SDK, or one runtime per active worktree. If neither is acceptable, use a pool of runtimes
   per worktree slot (e.g. four slots, matching `maxConcurrentAgents`).
2. **Enforce secret reads at the OS level.** The sandbox confines writes but allows reads everywhere, and
   that gap is what the guard's secret lists try to fill. On macOS, run the runtime under a `sandbox-exec`
   profile (the same mechanism Codex and Claude Code use) with `(deny file-read* (subpath "~/.ssh") …)`
   and `(deny file-read* (regex "/\\.env(\\..*)?$"))`, or better, an allowlist of readable roots: the
   worktree, the toolchains, `/usr`, `/opt/homebrew`, the tmp dir. On Linux use bubblewrap or Landlock. Check whether
   Harness's shell sandbox already takes a read policy; if so, set it in the profile instead of adding
   another layer.

Once both are in place, the guard's job shrinks to "give the model a clear, early, structured refusal", which is
what the README already says it is.

### 2.3 Stop scraping rendered tool output

`service.js:872–904` reads fleet results by matching `workflow "…" completed (N agents).\nReturn value:` and
running `JSON.parse` on everything after the *last* `Return value:`. Problems:
- It is exactly the "scraping human-readable output" that the README and `sdk.js` header rule out.
- If a worker's own result text contains `Return value:`, `lastIndexOf` lands inside the JSON string and parsing fails
  (it degrades to the label fallback rather than returning corrupted data, but still).
- `parseWorkflowHeader` only matches `completed`, so a failed or partial run loses `runName`/`agentsStarted`.
- It forces `tool-workflow.maxResultChars: 250000`, which flows into the dispatcher's context (2.1).

**Change:** the service already receives per-member `tool-workflow/agent-start|end` (with label, childId, outcome)
and `subagent.finished` (with `lastAssistantMessage`). Build the result entirely from those, and delete
`BATCH_SCRIPT`'s return value and all text parsing. With 2.1-B the handler returns structured data directly.
If a field is missing from the events (e.g. the script's return value), ask upstream to add it to
`tool-workflow/run-end` rather than parsing the renderer.

### 2.4 One source of truth for the route and the limits

The pinned route `ollama` / `deepseek-v4.1-flash:cloud` is written in: `dsh-subagent-flash` `DEFAULTS`,
`install.mjs:patchBlock`, `flash-service/cordis.patch.yml` (four times: `llm-pi-ai`, `agent-default-model`,
provider row), the preset (`agentOptions`, persona text), `service.js` `DEFAULT_*`, `index.js` `parseOptions`
and `INSTRUCTIONS`/tool descriptions, and the README. Limits (4 concurrent / 32 total / 16 tasks / timeouts) are
spread out the same way, and the preset (`maxItemsPerCall: 32`) and service profile (`64`) already disagree.

Also, `flash-mcp --provider/--model` (and `FLASH_SERVICE_PROVIDER/MODEL`) look like operator knobs, but they
only change the *dispatcher's* `initialize` route. If they name a model the profile doesn't register, the
dispatcher fails. Workers ignore them.

**Change:** one `flash.config.json` (route, limits, protected lists) read by `install.mjs`, which *generates*
the profile patch and preset values, and read by `flash-mcp` at startup for descriptions and defaults. Remove
`--provider/--model` from `flash-mcp`, or make them fail if they disagree with the profile (read it with
`dsh --profile … --dump-config`).

### 2.5 Profiles and the installer

- **The read-only profile comes from string replacement** (`install.mjs:225–233`): `replaceAll('flash-service', …)`
  plus the *first* `mode: workspace-write`. Any comment or a reordered row silently changes what gets
  generated. Use Harness's own layering instead: `flash-service-readonly` = same bundles + `flash-service`'s
  patch + a one-row overlay `- id: sandbox-policy\n  config: {mode: read-only}`. Use a `--patch` overlay or a
  bundle that points at the base profile, if the loader supports one. Also add a post-install assertion:
  `dsh --profile flash-service-readonly --dump-config | grep 'mode: read-only'`.
- **Profile skeleton files are only seeded** (`seedFile`), so a bundle change in `profiles/flash-service/package.json`
  never reaches an existing install. Either manage `package.json` like the patch block, or warn when the files
  differ (today the message is easy to miss).
- **Custom profile names break read-only.** `--profile custom` makes the service ask for `custom-readonly`
  (`service.js:189`), which the installer never creates. Either take the read-only profile name as its own
  option, or generate it for whatever profile is installed.
- `withManagedBlock`/`withoutManagedBlock` slice `end + endMarker.length + 1`, which assumes a trailing `\n` and eats a
  character otherwise.
- There's no preflight: install doesn't check that Ollama is reachable or that the model is pulled
  (`ollama show deepseek-v4.1-flash:cloud`). Today a missing model shows up as a worker-turn error on the first
  call.

### 2.6 Preset: the stated child restrictions don't hold for `workflow`/`ralph`

`presets/flash-orchestrator/agent.cordis.yml`: the `toolFilter` that makes children read-only (deny bash, write,
edit, …) is on `tool-flash` only. `workflow-worker-thread` and `tool-ralph` start children through the same
provider **without** a filter, so workflow and Ralph children have bash and write access. The persona tells the
orchestrator otherwise only for `flash`, but README requirement #8 ("no unrestricted fs/shell") reads as if
it applies to all three.

**Change:** set `toolFilter` in the `subagent-flash-in-process` row config for the interactive profile, so it
applies at the single choke point every child passes through (the provider already merges filters). Or say
explicitly that workflow and Ralph children can write.

### 2.7 Process model

One `flash-mcp` per MCP client session, times one or two `dsh` runtimes, each lazily booted and kept forever.
Several Claude Code or Codex sessions multiply that. Sessions are never disposed inside a runtime (the protocol has no
session-close), so a long-lived runtime keeps growing.

**Change (pick):**
- **Minimum:** shut a runtime down after being idle (e.g. 10 min), and recycle it after N sessions or when
  RSS exceeds a limit, but only once no call is in flight.
- **Better:** a per-user daemon (`flash-mcp --daemon`, a Unix socket under `$DSH_HOME/run/`) that all stdio
  shims connect to. That gives one warm runtime per profile, one global concurrency limit (2.8), and cold start
  is paid once.

### 2.8 No limits across calls, and orphaned work

- Nothing limits concurrent `flash_task`/`flash_batch` calls on a runtime. The README says so ("plus any number of
  calls in flight"). Three parallel batches means 12 concurrent Ollama cloud requests, plus dispatchers.
- A timeout or cancel only stops *waiting* (`raceWithBudget`, `service.js:745`). The session keeps running
  and spending quota, and its tools keep changing the tree *after* the caller was told the call failed.
  Nothing counts or limits these orphans.

**Change:** a service-level semaphore (`FLASH_MAX_INFLIGHT`, default e.g. 2 calls / 4 workers). Track orphaned
sessions. When orphans exist and nothing else is in flight, recycle the runtime (SIGTERM is the only real
cancel available). Refuse new calls with `BUSY` when orphans exceed a threshold. Report `orphanedSessions` in
the runtime diagnostics. Push upstream for `session/cancel`.

## 3. Performance

Ordered by expected impact:

1. **Remove the dispatcher** (2.1): saves at least two model turns per call, output tokens proportional to the task,
   and the fleet result being re-read by the dispatcher.
2. **Shrink what the expensive caller receives.** Every tool result is sent twice: as pretty-printed JSON in
   `content[0].text` (`index.js:267`, `JSON.stringify(result, null, 2)`) and as `structuredContent`. Most
   clients put `content` into the model context. Batch results repeat per-member data in `results`, `workers`,
   and `routes`, and include `runtime.pid/uptimeMs/sessions`, which the calling model never needs.
   Budget: `perItemChars` 4000 in the script, *then* `maxResultChars` 8000 per item in the service. The effective
   budget is 4000, but the config suggests 8000, and 16 items × 4000 = 64 KB ≈ 16 k tokens of Opus/Sonnet
   context per batch.
   **Change:** `content` = a compact text rendering (one line of status, then per task `#i status: result`,
   plus denials and `filesChanged`). `structuredContent` = minimal JSON declared by an `outputSchema`. Move
   `runtime`, `workers`, `routes`, and `sessionId` behind `verbose: true` or into stderr. Use one budget knob per
   tool. Add a total batch budget (`FLASH_BATCH_MAX_CHARS`) and trim the longest items first.
3. **Cold start.** The first call pays for booting `dsh` (profile resolution, and pnpm if needed), then
   `initialize`, under the 30 s request timeout (`sdk.js:24`), which may be too short on a cold profile. The
   first `read-only` call pays it again. **Change:** optionally prewarm on MCP `notifications/initialized`
   (`FLASH_PREWARM=flash-service,readonly`). Give `initialize` its own, longer timeout. Log the boot
   duration.
4. **Duplicate prompt text in fleets.** `WORKER_RULES` and `Working directory:` are embedded in every item. Put
   shared text in the script (`const rules = args.rules`) or, better, in the provider's `persona` config
   (workflow children already go through the `flash` provider, which supports `persona`). Once the persona applies
   to fleet members, `WORKER_RULES` can be deleted.
5. **Fewer diagnostics on the hot path.** Every child start/finish/route, every orchestrator event (up to 40),
   every tool call/result, and every `dsh` stderr chunk is written to stderr (`service.js:592, 609, 629, 641, 674`;
   `sdk.js:154`). Claude Code keeps MCP stderr logs. Add `FLASH_LOG_LEVEL` (default `warn`).
6. **Minor:** `sdk.js:311` and `mcp.js:192` re-slice the whole buffer for every line and search it from the start
   on every chunk. That's quadratic on a 250 KB single-line frame. Track a scan offset, or use
   `readline`. `observe` does `[...workflowAgents.values()].find` per `agent-end` (fine at 16; use a
   `seq → agent` map).

## 4. Integration with Claude Code, Codex, and other MCP clients

### 4.1 Long blocking calls, no progress, client timeouts (P0 for Codex)

Calls block for up to `FLASH_TASK_TIMEOUT_MS` = 5 min and `FLASH_BATCH_TIMEOUT_MS` = 15 min. The server
advertises no progress (`mcp.js` header: "Deliberately not implemented: … progress"). Codex CLI's default
per-server `tool_timeout_sec` is 60 s, so a normal task will be abandoned by the client while the worker keeps
running (see 2.8). Claude Code has its own limits (`MCP_TOOL_TIMEOUT`). The live suite only works because it
passes `timeout: TIMEOUT_MS` explicitly (`verify-live.mjs:74`).

**Change:**
- Send `notifications/progress` when the request carries `_meta.progressToken`: on child started, on child
  finished (`progress: finished, total: requested`), and as a heartbeat every ~15 s. Clients that reset their
  timeout on progress then stop timing out.
- Add an **async door** alongside the blocking one: `flash_start {…} → {jobId}`,
  `flash_status {jobId} → {state, finished, total, partialResults}`, `flash_result {jobId, waitMs?}`. This is the
  most robust option across clients, and it lets the expensive agent keep working while the fleet runs.
- Document the per-client config in the README: a Codex `config.toml` block with `tool_timeout_sec`/`startup_timeout_sec`,
  Claude Code's `MCP_TOOL_TIMEOUT`, and a generic note.

### 4.2 Permissions: split tools by effect

Client permission systems (Claude Code `permissions.allow`, Codex approvals) work on **tool names**, not
argument values. With `mode` as an argument, a user can't auto-approve read-only delegation while still being
asked about writing delegation, even though that's the most useful policy.

**Change:** expose `flash_read` / `flash_read_batch` (always read-only profile, `annotations.readOnlyHint: true`)
and `flash_write` / `flash_write_batch` (`destructiveHint: true`, `openWorldHint: false`). Remove `mode` from the
schema, or keep it as a deprecated alias. Add `annotations.title`. The README's "Permissions" section becomes much
simpler: allow `flash_read*`, and get asked about `flash_write*`.

### 4.3 Server entry point fails to start under `npx`, `npm link`, or paths with spaces

`index.js:322`: `import.meta.url === \`file://${resolve(process.argv[1])}\``. `import.meta.url` is the
percent-encoded realpath. `argv[1]` is neither encoded nor realpath'd for a `bin` symlink
(`node_modules/.bin/flash-mcp`, `npm link`, `npx`) or for a path containing spaces or non-ASCII characters. In
those cases `main()` never runs: the process exits immediately with no output, and the client reports that the
server closed. **Change:** `import.meta.url === pathToFileURL(realpathSync(process.argv[1])).href`, or split
into a `bin/flash-mcp.js` that just calls `main()`.

### 4.4 Root selection per project

The README `.mcp.json` example hardcodes `/Users/thomas/...` for both the server path and `--root`. Because
`--root` pins one workspace per registration, a user-scope registration (`claude mcp add -s user`) points
every project at the same root.

**Change:**
- Default the root to the spawn cwd (already the case) and document the **project-scoped** registration
  without `--root`.
- Support MCP **roots**: if the client declares the `roots` capability, call `roots/list` after initialize and use
  the single root, or require `cwd` to be inside one of them. Handle `notifications/roots/list_changed`.
- Publish a runnable package (`npx flash-mcp` / `bin`) so config doesn't need absolute repo paths. This depends
  on 4.3.
- Refuse to start (or warn loudly) when the root is `$HOME`, `/`, or a directory with uncommitted changes, unless
  `--allow-dirty` is passed. The README's worktree advice is correct, but nothing enforces it (and 2.2 makes it
  unnecessary).

### 4.5 Protocol details

- **Cancellation response.** `mcp.js:125` sends a `-32800` error after `notifications/cancelled`. The MCP spec says
  the receiver SHOULD NOT respond to a cancelled request. Drop the response. The service's
  `FlashTaskCancelled` path is then just cleanup.
- **`outputSchema`.** `structuredContent` is returned without an `outputSchema`. Declare one (protocol
  2025-06-18) so clients can validate the output and show it.
- **Structured errors.** `FlashTaskError.code` is only in prose (`"flash_task failed: …"`). Also return
  `structuredContent: {error: {code, message}}` with `isError: true`, so the calling agent can branch on
  `TIMEOUT`, `BUSY`, `NOT_DELEGATED`, `CWD_OUTSIDE_ROOT`, and so on.
- **Schema consistency.** `flash_task` requires `cwd` (`index.js:88`), while `flash_batch` and the service treat it
  as optional and accept relative paths. The description says "Absolute". Make it optional, relative to the root,
  in both.
- **Error strings.** `optionalText` throws `"acceptance must be a string"` for any field (`service.js:985`). Pass the
  field name.
- **Config parsing.** `numberFrom` silently ignores invalid values (`FLASH_TASK_TIMEOUT_MS=5m` falls back to the default).
  Fail at startup instead. `FLASH_MAX_TOKENS` has no CLI flag.
- **Signal listeners.** `startServer` registers `SIGINT`/`SIGTERM` listeners on every call (`index.js:290`), which leaks
  listeners in tests and embedders. Register once in `main()`.
- The hand-rolled server is fine for scope and dependencies. But progress, roots, logging, and output schemas
  (4.1–4.5) are exactly what `@modelcontextprotocol/sdk` provides, and it's already needed for `verify`. Reconsider
  adopting it for the server side if these items get implemented. That's a judgement call, not a must.

### 4.6 What the caller learns

- **`filesChanged` / `diffstat`.** Today the calling agent has to trust the worker's prose. Compute these (from the
  worktree in 2.2, or from `git status --porcelain` before and after when running in the root, noting that it can't
  be attributed per task in a shared tree).
- **Usage.** `request/header` and `usage` events are observed but thrown away. Return
  `usage: {inputTokens, outputTokens, requests}` per call. That lets the caller (and the user) see that
  delegation actually saved money, which is the reason this project exists.
- **Server `instructions`** (`index.js:28`) should say when *not* to delegate (cross-file refactors, anything
  needing conversation context, security-sensitive edits). They should tell the caller that results are unverified
  and must be checked, and that tasks in one batch must touch disjoint files (until 2.2).

### 4.7 Machine-wide patch layers leak into the service

Already noted as a limitation in the README (`mcp__memorix__*` showed up in workers). For a service whose
premise is a narrow surface, that isn't acceptable. **Change:** have the service profile explicitly
restrict tools to an allowlist for workers (bash, read, write, edit, glob, grep), or disable known
machine-wide MCP rows. At minimum, fail `verify` if the worker's `request/header.tools` contains anything outside the
expected set (the header is already observed).

## 5. Tests and verification

- **Tests are checked against invented event shapes.** `FakeSdkClient` and `fake-dsh.mjs` produce the event shapes the
  service expects, so the tests can't catch drift in real Harness events. **Change:** record a real
  notification transcript per scenario (task, batch, denial, non-delegation) from a live run into
  `test/fixtures/*.jsonl`, replay it in `service.test.mjs`, and re-record when the `dsh` version changes (store the version
  in the fixture).
- **The `node --test` hazard.** Instead of the README warning, move `fake-dsh.mjs` → `test-support/fake-dsh.mjs`
  and `verify-live.mjs` → `scripts/verify-live.mjs`. Anything under a `test/` directory matches Node's default glob.
- **Guard regression corpus.** Add every bypass from §1.1 as a test. Add a small property/fuzz test: for
  `rm -rf X`, where X is any spelling that resolves to the root (`.`, `./`, `$PWD`, `"$(pwd)"`, the absolute
  path, `../<name>`, a symlink), the guard must deny.
- **Live suite:** runs in a clone (§1.3). Add stages for progress notifications (4.1), `BUSY`/orphan handling (2.8),
  read-only tool split (4.2), and "worker tool surface is exactly the allowlist" (4.7).
- **No CI.** Add a GitHub Actions workflow running `npm test` on Node 20/22/24 on macOS and Linux (the path-handling
  code has macOS-specific branches: `/var` → `/private/var`).
- **README counts have drifted** ("16 tests" vs "17 wall tests" vs the actual number). Generate the counts, or drop them.
